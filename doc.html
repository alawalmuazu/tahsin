System Architecture · v7.0.0

Tahsin / SmartSchool

CodeIgniter 3 school-management platform customized for Kaduna State — a single deployment covering many schools under education boards such as KADSUBEB and KADSSSEB.

1. What the app is

Tahsin is a multi-tenant school ERP branded SmartSchool. It started from a commercial multi-school product (Ramom School lineage) and has been extended for state-government use. Stack: PHP, MySQL/MariaDB, Apache with .htaccess rewriting. App version is 7.0.0.

It adds two layers on top of a normal single-school product:

  1. School (branch) — one school’s students, staff, fees, attendance.
  2. Education board — shared curriculum, classes, subjects, and standards that cascade to every school on that board.
  3. State — Super Admin / statewide roles see all schools, NEMIS reports, inspections, transfers, and analytics.

2. How a request moves through the code

Browser
  → index.php (front controller)
  → application/config/routes.php
  → MY_Controller (install check, global settings, timezone, branch currency)
  → Admin_Controller / User_Controller / Frontend_Controller / Authentication_Controller
  → module controller (Student, Fees, Exam, …)
  → model + MySQL
  → views/layout/index.php (header + sidebar + $sub_page)

index.php is the only public PHP entry. Environment comes from CI_ENV or a .env file; production is not hardcoded.

Autoload (application/config/autoload.php) always loads:

  • libraries: database, session, form_validation, upload, app_lib
  • helpers: url, form, security, general
  • model: application_model

Almost every staff screen extends Admin_Controller, which redirects to /authentication if the session is missing.

A typical staff action looks like Student:

  1. Extend Admin_Controller.
  2. Resolve school with $this->application_model->get_branch_id().
  3. Validate with CI form_validation.
  4. Write through a model.
  5. Render layout/index and set $this->data['sub_page'] to the inner view.

Super Admin can pick any branch_id (usually from a POST). Everyone else is locked to get_loggedin_branch_id().

5. Multi-tenancy: branch + board

This is the most important design in the repo.

  • branch = one school.
  • education_board = a board that owns many schools.
  • branch.board_id links a school to a board.
graph TD STATE["State / Super Admin"] BOARD1["KADSUBEB Basic Ed"] BOARD2["KADSSSEB Senior Sec"] SCHOOL1["LEA Primary"] SCHOOL2["JSS Kawo"] SCHOOL3["Govt College"] STATE --> BOARD1 STATE --> BOARD2 BOARD1 --> SCHOOL1 BOARD1 --> SCHOOL2 BOARD2 --> SCHOOL3

Shared catalogs (class, subject, section, staff department, designation, and similar) use a hybrid load in App_lib::getHybridItems():

  • rows owned by the school’s board_id, plus
  • rows created only for that school (branch_id set, board_id null).

Hybrid loading

The board sets NERDC-style classes/subjects once; a school can still add local extras. Super Admin manages boards in Education_board. Academic years are a second axis: most student data is scoped by session_id via get_session_id().

Enrollment is not “student lives in a class forever.” A student row is linked to a school/class/section per session via enroll.

6. Identity and access

All logins go through /authentication and the login_credential table. login_credential.user_id points at the entity row. Passwords are hashed (MY_Model::hash() / pass_hashed()).

RoleEntity tablePortal
1staffSuper Admin — all branches
2+ staff rolesstaffSchool back office
6parentParent dashboard
7studentStudent dashboard

Super Admin always passes get_permission(). Other staff roles use staff_privileges + permission. Statewide roles are flagged with roles.is_statewide and checked via is_state_executive_loggedin().

Credential lifecycle

There is a hybrid credential flow (not just “admin types the password”):

activeMeaning
2Pending setup (invite token)
0Pending admin approval
1Live
  • Public signup is Registration.
  • Approvals are Credential_approvals.
  • CSV import can create students, staff, and parents without passwords, then send setup links.
  • Student NIN is validated statewide (unique_nin in Student).

Students and parents use a different sidebar (userrole/sidebar) and a lighter dashboard.

9. How views are assembled

Staff pages almost never load a full HTML file themselves. They set:

  • $this->data['title']
  • $this->data['sub_page'] — e.g. 'student/view'
  • $this->data['main_menu'] — sidebar highlight

Then they call $this->load->view('layout/index', $this->data).

layout/index.php wraps header, topbar, sidebar, and the inner page. Public marketing pages go through Home and branch-specific CMS settings.

11. How to find your way around a feature

  1. URL tahsin/fees/collect → application/controllers/Fees.php method collect.
  2. Matching model: application/models/Fees_model.php.
  3. Views: application/views/fees/.
  4. Data is almost always filtered by branch_id and often session_id.
  5. Shared lists (classes, subjects) go through App_lib::getHybridItems(), not a raw WHERE branch_id = ….

12. Database highlights

The dump in smartschool.sql has 100+ tables. User entities sit under one login table.

Parent & student model

One parent can have many students via student.parent_id. login_credential authenticates all three entity types. Students belong to a school/class through enroll for the current academic session.

13. CSV import / export

Bulk operations are standardized across the three main entity types. Password hashes are never exported.

EntityImportExportNotes
Students Existing Added Exports guardian details. Scoped by branch and session. NIN unique statewide.
Employees Upgraded Added Dedicated page (not AJAX modal). Exports joining role / designation.
Parents New New Creates login_credential rows; can leave passwords unset and send setup invites.

Security

CSV exports include username for cross-reference but exclude password hashes. Imported accounts typically start at active = 2 until the user sets credentials via the tokenized setup link.
